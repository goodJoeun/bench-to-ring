# 업적 난이도 등급과 달성률

업적을 동메달·은메달·금메달·MVP 트로피 네 등급으로 나누고, 업적마다 달성한 플레이어 비율을 보여줘요. 2026-11-27에 측정하고 넣었고, 2026-11-28에 수비 업적 13종을 같은 방법으로 재서 더했어요(모두 123종). 등급표는 `src/game/legacy/achievement-tiers.ts`, 달성률은 `src/server/leaderboard/achievements.ts`와 `drizzle/0007_achievements.sql`이에요.

## 1. 난이도 등급

### 측정 방법

- 국적 10개마다 1,500명씩, 포지션과 플레이 유형을 고르게 섞어 은퇴까지 돌렸어요. 플레이마다 1만 5천 커리어예요.
  - **일반 플레이**: 선택지를 무작위로 골라요. 투자·구입·기부는 하지 않아요(`npm run balance`와 같아요).
  - **최적화 플레이**: 랭킹 점수가 가장 오르는 선택을 고르고, 훈련 초점·투자·장비 구입·기부를 챙겨요.
  - **한 팀 충성 플레이**(보정용, 6천 커리어): 최적화 플레이와 같되 지금 팀과 재계약을 먼저 고르고 트레이드를 거절해요. 원클럽맨처럼 봇이 노리지 않는 업적을 노리고 하면 얼마나 되는지 봐요.
- **수비 업적**(2026-11-28)은 국적 10개마다 500명씩, 아래 네 플레이로 같은 커리어(같은 시드)를 5천 개씩 돌렸어요.
  - 일반·최적화·한 팀 충성 플레이는 위와 같아요.
  - **수비 키우기 플레이**: 최적화 플레이와 같되 훈련 초점을 수비가 99가 될 때까지 수비, 다음은 운동능력에 두고, 투자도 수비 캠프를 먼저 해요. 수비 업적을 노리는 플레이예요.
  - 수비 키우기를 노리는 플레이에 더해도 기존 업적의 등급은 그대로예요(모든 것을 막는 방패 p 11.5%로 은메달, 통곡의 벽 2.9%로 금메달).
  - 엔진이 준 업적과 측정 조건이 커리어마다 같은지 1,600 커리어로 맞춰 봤어요.
- 달성률은 국적마다 같은 비중으로 평균했어요. 병역 업적은 대한민국 선수만 셌어요.
- 돈으로 따는 업적(사치품 중독자, 기부천사, 아낌없이 주는 나무)은 봇이 사거나 기부하지 않아서, 그만큼 벌었는지로 셌어요(사치품 5종 32.58억, 누적 기부 1,000억, 기부 100억이 번 돈의 절반이 되려면 200억).

### 등급 기준

- **기준 달성률 p**: 일반 플레이 달성률과 '노리는 플레이'(최적화·한 팀 충성, 수비 업적은 수비 키우기까지 가운데 더 잘 따는 쪽) 달성률의 기하평균이에요. 노리는 플레이가 오히려 덜 따는 업적(새가슴, 대한민국 육군처럼 봇이 피하는 업적)은 일반 플레이 달성률을 써요.
- **등급**: p로 따기까지 드는 커리어 수(약 1/p)를 봐요.

| 등급 | 기준 달성률 | 따기까지 커리어 수 | 업적 수 |
| --- | --- | --- | --- |
| 동메달 | 20% 이상 | 5번 안 | 38 |
| 은메달 | 5~20% | 5~20번 | 48 |
| 금메달 | 1~5% | 20~100번 | 20 |
| MVP 트로피 | 1% 미만 | 100번 넘게 | 17 |

- **누적 기록 업적**: 커리어를 이어서 플레이할 때(포지션은 돌아가며, 국적은 무작위) 따기까지 걸린 커리어 수의 중앙값이에요. 일반·최적화의 기하평균에 위와 같은 커리어 수 기준을 써요.
- **역대 랭킹 업적**: 전체 기록 12,306건 가운데 TOP 10은 상위 0.1%이고, 기록이 가장 적은 PF도 1,511건 가운데 TOP 10이라 상위 0.7%예요. 모두 MVP 트로피이고, 기록이 쌓일수록 더 어려워져요.
- **경계에 있는 업적**(기준선과 1.25배 안): 3월의 광란(20.3%), 저니맨(24.9%), NBA 왕조 건설(4.6%), 반지의 제왕(18.1%), 만년 2인자(6.1%), 무관의 제왕(1.2%), 시즌 트리플더블(22.3%), 초신성의 등장(1.2%), 나이는 숫자에 불과(5.3%), 얼음 심장(24.2%), 토종 슈퍼스타(19.2%), 슛했다 하면 골인(23.8%), '볼'아일체(1.1%), 농구 도사(19.3%), 신데렐라 스토리(19.2%), 월드 투어(4.7%), 세계 최강(22.5%), 불혹의 현역(20.6%), 기부천사(17.6%), 예비역의 반란(17.5%), 자물쇠 수비(21.1%), 수비가 우승을 만든다(24.7%). 실제 달성률(2장)이 쌓이면 이 업적부터 다시 보면 좋아요.
- 일반 플레이는 무작위 선택이라 실제 사람보다 약해요. 등급은 상대적인 난이도로 보고, 실제 달성률이 모이면 그걸로 다시 맞추는 게 정확해요.

## 2. 업적별 달성률과 요금제

### 지금 사용량

배포 사이트의 공개 통계(`GET /api/boards/days`, 2026-11-27 기준)예요.

- 올린 은퇴 기록 12,306건, 기록을 올린 플레이어(기기) 2,825명
- 최근 6일(11-21~26) 하루 458~578건, 그날 기록을 올린 플레이어 189~257명

### 구조: 은퇴 기록 제출에 얹기

- **보내기**: 은퇴 기록을 올릴 때(`POST /api/careers`) 이 브라우저에서 딴 업적 id 목록(`b2r-achv-v1`의 키)을 함께 보내요. 요청 수가 늘지 않아요. 이 기능 전에 딴 업적도 다음 은퇴 때 같이 올라가요.
- **저장**: `player_achievements (player_id, achv_id)`를 기본키로 두고 `ON CONFLICT DO NOTHING`으로 한 번만 넣어요. 새 줄이 생길 때 트리거가 `achievement_counts (achv_id, players)`를 1 올려요. 지금 `career_counts`·`career_totals`와 같은 방식이에요.
- **달성률**: 업적의 `achievement_counts.players`를 업적 목록을 보낸 플레이어 수(`'*'` 줄의 `players`)로 나눠요. 이 기능 전에만 기록을 올린 플레이어는 분모에 들지 않아요.
- **조회**: `GET /api/achievements`가 집계 표(업적 수만큼, 약 120줄)만 읽어요. 순위표처럼 `'use cache'` + `cacheTag`와 CDN `s-maxage=300, stale-while-revalidate=3600`을 붙이고, 업적 창을 열 때만 불러요. 첫 화면 요청은 늘지 않아요.
- 업적을 딸 때마다 서버에 보내는 방식은 요청이 플레이어마다 수십 배로 늘어서 권하지 않아요.

### 부하 추정

| 항목 | 추정 | 한도 |
| --- | --- | --- |
| 제출 요청 | 늘지 않음 (하루 약 550건 그대로) | |
| 제출 본문 | 업적 id 목록 최대 약 2KB 추가 | 지금 제한 16KB (`MAX_BODY`) |

### 판단

**업그레이드는 필요 없어요.** 달성률 기능은 지금 사용량에서 Supabase 무료 한도의 몇 %도 쓰지 않고, Vercel 비용도 사실상 늘지 않아요.

따로 지켜볼 것은 업적과 상관없는 **DB 용량**이에요. 운영 DB(2026-11-27 확인)는 전체 38MB, 은퇴 기록 표 26MB, 기록당 2,186B예요. 하루 약 520건씩 올라와 한 달에 약 34MB씩 늘어서, 이 속도면 500MB까지 1년 남짓(2027년 말쯤) 남아요. 300MB를 넘으면 다시 보고, 이용자가 지금의 10배쯤 되면 그때 Pro($25/월, 디스크 8GB)를 검토하면 돼요.

## 3. 은퇴 기록 크기 최적화

### 측정

운영 DB는 직접 읽지 않고, 로컬 Postgres(PGlite, 테스트와 같음)에 `drizzle/`의 마이그레이션을 모두 넣은 뒤 시뮬레이션 은퇴 요약 3,000건을 `insertCareer`와 같은 칸으로 넣어 쟀어요(국적·포지션·일반/최적화 플레이 섞음, 플레이어당 기록 4.4건).

- **기록당 2,245B** = 표 본문 1,513B + 인덱스 729B (13개)
- **은퇴 요약(jsonb)은 이미 압축돼 있어요.** 95%의 기록이 Postgres 기본 압축(pglz)으로 저장되고, 평균 1,183B예요(JSON 글자로는 1,508B).
- 요약 안에서 큰 것은 리그별 몫 `leagues` 581B, 거친 팀 `teams` 180B, 상 `awards` 122B, 캐릭터 `look` 119B, NBA 몫 `nba` 99B(`leagues.nba`와 겹쳐요)예요.
- 인덱스는 순위 두 개(`careers_pos_rank` 85B, `careers_rank` 74B), 중복 제출 막기 71B, 스탯 랭킹 여섯 개(각 52~57B), 플레이어별 57B, 기본키 52B 순이에요.

### 방법별 효과

| 방법 | 기록당 | 지금보다 | 기존 기록 |
| --- | --- | --- | --- |
| 지금 | 2,245B | | |
| `VACUUM FULL` (표와 인덱스 다시 쌓기) | 2,064B | -8% | 바로 줄어요. 코드 변경 없음 |
| 위 + `careers_player` 인덱스 빼기 | 약 2,007B | -11% | 마이그레이션 한 번. 플레이어별 쿼리는 중복 제출 막는 인덱스(`player_id, career_id`)로 읽어요(실행 계획 확인) |
| 요약에서 칸과 겹치는 키·`nba` 빼기 | 2,037B | -9% (`VACUUM FULL`만 한 것보다 -1%) | 기존 기록을 다시 써야 해요 |
| 압축 기준(`toast_tuple_target`) 낮추기 | 2,122B | 오히려 늘어요 | |
| 요약을 앱에서 gzip해 bytea로 저장 | 약 -10% (요약 813B, 대신 순위표가 읽는 `look`·팀·상 칸 약 150B 추가) | | 순위표·스탯·챌린지 쿼리와 `db:rescore`를 고쳐야 해요 |

- 겹치는 키를 빼도 거의 줄지 않는 건, 요약이 작아지면 압축 기준(약 2KB)보다 작아져서 압축하지 않고 저장되기 때문이에요(압축된 기록 95% → 65%).
- lz4 압축은 PGlite가 지원하지 않아 재지 못했어요. 보통 크기보다 속도를 위한 설정이에요.

### 기존 기록도 줄어드는지

- **형식을 바꾸면 새 기록에만 적용돼요.** 기존 기록은 `UPDATE`로 다시 써야 해요.
- **다시 쓰는 순간에는 오히려 커져요.** 옛 줄이 죽은 행으로 남아 표가 약 1.8배(기록당 2,245B → 4,052B)가 됐어요. 보통 `VACUUM`은 그 자리를 새 기록이 다시 쓰게 표시만 해서 크기가 그대로였고, `VACUUM FULL`을 해야 줄었어요.
- **운영 DB에는 이미 빈 공간이 있을 수 있어요.** 점수 계산을 바꿔 `db:rescore`를 돌릴 때마다 바뀐 기록이 다시 쓰였어요. 새 기록이 그 자리를 채우긴 하지만 파일 크기는 줄지 않아요.

### 운영 DB 확인 결과 (2026-11-27)

전체 38MB, `careers` 26MB, 기록당 2,186B로 로컬 측정(2,245B)과 비슷해요. 쌓인 빈 공간이 거의 없어서 지금은 `VACUUM FULL`을 할 필요가 없어요. 나머지 약 12MB는 Supabase 기본 스키마와 다른 표예요.

### 권하는 순서

1. Supabase SQL Editor에서 크기를 확인해요. `careers_total`이 `n_live_tup × 2.2KB`보다 많이 크거나 `n_dead_tup`이 많으면 빈 공간이 있는 거예요.

   ```sql
   select pg_size_pretty(pg_database_size(current_database())) as db,
          pg_size_pretty(pg_relation_size('careers')) as careers_heap,
          pg_size_pretty(pg_indexes_size('careers')) as careers_indexes,
          pg_size_pretty(pg_total_relation_size('careers')) as careers_total,
          s.n_live_tup, s.n_dead_tup
   from pg_stat_user_tables s where s.relname = 'careers';
   ```

2. 빈 공간이 크면 이용자가 적은 시간에 `VACUUM FULL careers;`를 한 번 돌려요. 표를 다시 쓰는 동안(지금 크기면 몇 초) 표가 잠겨서 제출과 순위 계산이 잠깐 기다리고, 표 크기만큼 여유 공간이 잠깐 필요해요. 잠그기 싫으면 `REINDEX TABLE CONCURRENTLY careers;`로 인덱스만 다시 쌓아요.
3. `careers_player` 인덱스는 업적 달성률 마이그레이션(`0007_achievements`)에서 뺐어요(-2.5%).
4. 요약 형식을 바꾸는 건 1% 남짓이라 권하지 않아요. 500MB에 가까워지면 형식을 손보는 것보다 Supabase Pro로 올리는 게 싸고 안전해요.
